01 / about

The unglamorous, correct parts.

I currently work on a Bharat Bill Payment System (BBPS) routing platform at a payments bank, moving bill payments from a central network out to downstream billers. My work lives where correctness is non-negotiable: making sure a payment settles once no matter how many times the network retries it, degrades gracefully when a single biller goes down, and reconciles cleanly the next morning.

I care most about behaviour under concurrency and failure — idempotency, isolation, blast-radius containment, and honest guarantees. Before this I built Java backends at Accenture. I write about system design to keep the reasoning sharp, not just the pattern.

02 / selected work

Three problems from one system.

Deep-dives into a production bill-payment platform. Details are generalized — the shape of the problem and the decisions behind each solution.

CASE 01

Exactly-once processing

Problem
The same payment instruction can arrive more than once — network retries, at-least-once queue delivery, upstream re-sends. Routing or charging a bill twice is unacceptable.
Approach
An idempotency layer keyed on transaction identity, using a create-only write as an atomic check-and-set: the write succeeds only if the key doesn't already exist. The first arrival commits; every duplicate short-circuits to the already-computed result instead of reprocessing.
stack — Kafka · Aerospike (create-only) · Spring Boot
CASE 02

Graceful degradation

Problem
The platform routes to many downstream billers, each with its own reliability. One slow or failing biller must not stall the pipeline or cascade into a wider outage.
Approach
Per-biller circuit breakers isolate failures so a single bad dependency trips only its own path. Feature flags let specific billers or flows be shed or switched to a fallback without a deploy.
stack — Resilience4j · Spring Boot · feature flags
CASE 03

Reconciliation & settlement

Problem
A routed payment isn't done until it's confirmed against the network and the biller. Settlement is next-day and asynchronous, and states can drift out of agreement.
Approach
An asynchronous reconciliation flow ingests settlement records, matches them against the platform's own view of each transaction, and drives status transitions to a final state — surfacing mismatches for review rather than swallowing them.
stack — Kafka · PostgreSQL · scheduled batch · ELK
